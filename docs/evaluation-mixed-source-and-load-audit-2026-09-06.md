# Mixed-source and load evidence audit

## Decision

Keep the new joined integration contract as evidence that the current candidate's
state crosses the source, dialogue, feedback and recovery boundaries. Do not
convert it into live answer quality or production-capacity evidence. The earlier
G6 result supports explicit bounded provider concurrency in development; deployed
load qualification remains open.

## Quantity and coverage

The [final mixed-source trial](../research/05_evaluation/mixed-source-candidate-recovery-development-001-attempt-006-results.md)
contains **one joined scenario**, four synthetic sources in three formats, two
courses, seven student turns and 143 sequential assertions with 108 distinct labels.
The six course-A learners are deliberately minimal: five produce real-service gap
signals and the sixth supplies an active learner without a gap. The seventh
learner belongs to the sentinel course. These are not independent statistical
samples, and the assertion count is not an accuracy denominator.

The candidate/profile, source version, course authority, queue and recovery state
are connected in the same actual staging application. Credential/session and
Origin middleware run; a cross-origin mutation is rejected without side effects.
A source job cannot cross from course B into a course-A release even under common
professor ownership. After clean restore with the original directory moved aside,
source bytes, review audit, learner state and withdrawal remain effective; an
active other-course turn still uses its own source. A separate routine regression
also reads a restored PDF crop and rejects the wrong learner.

Four failed setup attempts are retained individually, followed by the initial
journey pass and expanded final pass. They expose and correct harness assumptions
about dataclass settings, qualification binding, profile identity and approved
domain models. They do not show four product/model failures. No actual software
defect was found in the final joined contract. Approved onboarding is a synthetic
setup fixture. The existing immutable binding enables the staging base but does
not qualify the injected question-specific candidate.

## Load-method assessment

| Evidence | What it supports | Important missing measurement |
| --- | --- | --- |
| G6 serial001 and concurrent002 | Actual shared-service/model calls, 25 queued routes, provider peak 1 versus 5; 100 POSTs and 150 calls each; persistence and identity contracts | Authenticated deployed load, network/TLS, browser, Docker, distributed workers |
| Observed p95 148.576s versus 31.968s | Descriptive effect consistent with removal of serialized provider waiting | Co-resident processes, no repeated randomized comparison, no sustained arrival-rate or saturation curve |
| 0 HTTP/provider failures | Finite operational request contract | Candidate had one safe graph failure and three no-evidence responses; nonempty200 is not tutoring quality |
| Mixed-source credentialed recovery | Internal authentication and restored authority/source behavior | No live provider, concurrent auth load, browser or actual TLS handshake |
| Mixed-source peak RSS | One bounded in-process contract's memory observation | G6 process peak RSS and memory growth under sustained model-backed load were not measured |

The predeclared G6 workload is a closed group of 25 clients, each issuing four
sequential turns. It is not an independent arrival process or evidence of unlimited
scale. No statistical confidence bound, uptime claim or causal learning benefit
can be obtained by multiplying its request count. Its candidate remains an
explicit cap-five option; the serial default and selected profile are unchanged.

## Remaining qualification plan

A later deployment experiment must freeze the exact candidate, server topology,
provider ceiling/configuration, authentication and source package together. Use a
fresh isolated deployment and synthetic credentials; verify one successful mixed
source/citation/withdrawal/recovery journey before applying load. Define the
student-facing latency/deadline requirement before selecting a load pass threshold.
Then predeclare arrival pattern, concurrency levels, duration, repetitions and
stopping rules; retain every failure and repeat. Measure end-to-end authentication
and tutoring latency, provider queue/service time and overlap, rate-limit errors,
semantic safe-failure actions, CPU/RSS, calls/tokens/reservations/cost and durable
message counts. Reuse the candidate's finite admission caps and do not retune
answers on the load packet. An independent content review remains a separate gate.

This plan is not a claim that a live deployed trial ran. Increasing the existing
TestClient request count cannot close those missing boundaries.

## Authenticated network successor

The previously missing real-network/provider combination was executed as
[`authenticated-loopback-load-development-001-live-001`](../research/05_evaluation/authenticated-loopback-load-development-001-live-001-results.md).
An isolated owned Uvicorn server, actual credential/session/Origin middleware and
real Luna provider completed 180 POSTs across six fixed 5/25-learner bursts. All
six unchanged 15-second route p95 gates passed; high-load p95 values were
14.375/14.101/13.310 seconds. All 360 messages persisted, and no HTTP, provider,
lineage or non-answer failure was observed. Source hashes matched the archived
snapshot. Two earlier injected network contracts remain separately registered,
including the initial evaluator shutdown-evidence failure.

This closes the missing authenticated loopback/live-provider measurement for the
explicit v3/1500-token candidate. It does not close public deployment, sustained
open-loop arrivals, overload beyond25 learners, many-turn/long-context workloads,
recovery under load or pedagogical quality. There are two repeated factual
question templates and six dependent operational repetitions, not180 independent
quality cases. The selected/default profile remains unchanged.
