# プロダクトの体験と標準図の対応案

## 発表の軸

教授が授業資料・指導方針・支援の条件を設定し、その範囲で学生への問いかけや質問対応を行う、授業ごとの学習支援アプリ。学生が質問する前にシステムから働きかけることもでき、その後の対話と活動記録を継続して扱う。

冒頭では同じ教授・同じ授業・同じ学生を追う。実画面で何が届いたかを示し、全体フローで誰が何をしたかをつなぐ。その後の設計図・比較・結論でも、同じ授業と学生に戻って説明する。

現在の31枚のPPTXと動画は、この案をまだ反映していない。この文書と初回フロー図は、日本語による構成確認用。既存の構成案・納品ファイルを上書きしない。

## 本編に使う表現

| 観客の疑問 | 採用する図・表 | このプロダクトで示す内容 | 対応するSDLCの説明 |
| --- | --- | --- | --- |
| 誰が何に使うソフトなのか | 実画面とC4システムコンテキスト図 | 教授、学生、授業のアシスタント、設定に応じた外部モデルとの関係。実際のメッセージを先に見せる | 利用者、目的、システムの範囲 |
| 準備から学習まで、誰が何をするのか | **UMLアクティビティ図（責任ごとのパーティション）** | 教授の公開、学生の参加と同意、質問前の初回支援、学生の返信、記録。条件を満たさない配信は見送る | 利用シナリオと機能要求 |
| なぜ学生が質問していないのに動くのか | **UMLシーケンス図** | 授業を開く、会話の枠を作る、ワーカーが目標を作る、復習時期に候補を作る、確認後に受信箱へ保存する。時間経過を明示する | 実行時の責務と連携 |
| どの部品がこの体験を実現するのか | **C4コンテナ図** | React画面、API、バックグラウンドワーカー、SQLite、教材ファイル、設定に応じた外部推論。APIとワーカーが共有する保存先 | アーキテクチャ設計 |
| 別の日にも続けるため、何を保存するのか | **ER図（Crow’s Foot記法）** | 学生、公開版、会話、学習目標、観測記録の主要な実テーブルと多重度。概念上の関連と実際の外部キーを混同しない | データ設計 |
| 支援をいつ継続し、いつ終えるのか | **UML状態機械図** | 学習目標のactive / completed / expired / cancelled。配信回数の上限は完了ではない。一時停止は配信の制御として区別する | ライフサイクルと運用制御 |
| 試した設計は、どこで失敗したのか | 同じ範囲のUMLアクティビティ図、比較表、実測グラフ | 同じ入力と期待する出力を置き、以前の処理と採用した処理の差分を示す。失敗例と測定結果を結びつける | 検証、設計変更、判断 |
| 現在のベストと次の改善は何か | 要求・設計・検証結果の対応表、優先順位表 | 現在採用している構成、比較上の利点、未達の要求、次の検証と判断基準 | 受入評価と継続開発 |

図の種類を揃えることを目的にしない。ユースケース図はC4と全体フローで役割が伝わる限り追加しない。クラス図とER図の重複、全クラスを載せた実装図、本編で説明しない配置図は増やさない。

## 初回フローの範囲と実装根拠

作成した[日本語のUMLアクティビティ図](../diagrams/product-first/01-agent-initiated-activity-ja.drawio)は、コードに基づく初回復習シナリオを表す。新しく録画・実測した動作結果ではない。

1. 教授が教材・目標・方針を公開し、自律支援を有効にする。学生は受講登録済みで受信に同意する。
2. 授業画面を開くと、質問を送らなくても会話の枠を作成できる。
3. 既定のイベント監視は、会話の枠がある対象学生について、教材・方針などが有効なら学習目標を作成できる。
4. 現行版の会話があり、先に該当する別イベントなどがない初回シナリオでは、目標作成から24時間以降に復習の候補になる。
5. 候補になっただけでは配信を保証しない。教材、権限、頻度、生成内容、保存時点の権限などを確認する。
6. 許可された支援をアプリ内受信箱へ保存する。学生が内容を確認してチャットで回答すると、その対話と評価可能な観測が記録される。

| 確認事項 | 実装・既存テスト |
| --- | --- |
| 質問前に会話の枠を作る | `apps/web/src/hooks/use-student-workspace.ts` の `createStudentConversation` |
| 会話がある学生について目標を作る | `src/digital_twin/student/autonomy_service.py` の `observe_events` |
| 復習時期の検出と先行イベント | 同ファイルの `_observed_event` |
| 受信箱の表示とReply in chat | `apps/web/src/components/student/student-workspace.tsx` |
| 教授の予約配信という別経路 | `src/digital_twin/student/proactive.py` の `schedule_trigger`、`tests/digital_twin/test_proactive_outreach.py` |
| 現行の支援判断に使う簡易入力 | `src/digital_twin/student/planning_architectures.py` の `default_planning_state_card` |

教授が時刻と内容を指定する予約配信は、質問履歴も会話の枠も前提にしない別経路。予約配信とイベント検出による判断を一つの矢印にまとめ、自律性を過大に説明しない。

現行の自動監視は、会話が全くない新規学生に、受講登録だけで初回メッセージを発生させるわけではない。最初の質問が不要であることと、参加直後に無条件で送信されることは区別する。

## 図をまたぐ接続のルール

現実の実装と関数名・疑似コードを対応させる詳細は、[実装に基づく図とコード例](implementation-backed-examples-ja.md)に追加した。初回図の単純化をそのまま最終版にせず、全体モデルから接続する詳細図で起動・分岐・保存・再試行・終了を追えるようにする。

- 全体フローの動作名と、詳細図の処理名を対応させる。「復習時期を検出する」を詳細図で突然「orchestration」など別の抽象語に置き換えない。
- C4の要素名をシーケンス図の参加者名に引き継ぎ、ER図の保存対象をシーケンスの読み書きと対応させる。
- 本文に「この図で分かること」を一文置く。矢印だけで原因やデータの意味を推測させない。
- UMLの開始・終了、分岐条件、メッセージ、状態遷移を使い分ける。色に独自の動作上の意味を持たせない。
- 全体フローは一つのシナリオの終了まで。学習目標の終了や次の仕事の再評価は別の状態図・詳細図で説明する。
- 正誤などの記録と支援判断の現行入力は、実装どおりに分ける。「記録→最適な次の指導」という未実装・未検証の接続は描かない。
- ER図では物理的に存在しない学習目標と評価の外部キーを描かない。アプリケーションが同じ学生・公開版・概念で照合するルールを説明する。
- 失敗した設計と現在の設計は、同じ入力・同じ図の範囲・同じラベルで比較する。比較実験の候補を現行システムに組み込まれた部品として描かない。
- 本番スライドは英語。日本語版は内容と接続を確認するための素材。英語化の際に見出しと余白を再調整する。

## 標準と作図ツール

- [OMG UML 2.5.1](https://www.omg.org/spec/UML/2.5.1/About-UML)：動作・相互作用・状態の記法。
- [C4の図の種類](https://c4model.com/diagrams)：構造の説明。C4はUMLとは別のモデルであり、4階層すべてを使う必要はない。
- [draw.ioのCrow’s Foot解説](https://www.drawio.com/docs/tutorials/crows-foot-notation/)：ER図の多重度。
- [draw.ioのUML解説](https://www.drawio.com/docs/diagram-types/uml/)：作図に使用する記号と用途の確認。

draw.ioは編集ツールとして使用する。記法はUML・C4・Crow’s Footから選び、図ごとに明記する。編集可能な`.drawio`と画像出力を保持する。
