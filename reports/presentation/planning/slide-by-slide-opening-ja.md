# 冒頭5枚の制作設計と全編の接続

2026-09-08。承認済みの[全体構成](presentation-structure-brief-aligned-ja.md)を、一枚ずつ制作するための具体化。ここではスクリプトとPowerPointを制作せず、載せる情報・図の役割・読者が理解する内容を定める。

## 全編に共通する判断

発表の問いは「このソフトウェアは何を実現したか、現時点ではどの構成が最も妥当か、継続的な学習支援には何を改善すべきか」。教授の正式な3本柱を要求として使い、各章では動く機能、設計、比較・失敗、判断をつなぐ。

各ページには、主題を特定できるタイトル、図や画面を読むための短い説明、そのページの結論を置く。ただし表紙と目次には結論文を強制しない。説明の量は一律に削らず、読者が口頭の補足なしで関係を理解するための情報を残す。

IT5004の一つの利用場面を共通例にする。教材を公開し、学生が「商品ページは直接データベースを操作してよいか」を尋ね、回答を受け、後の支援や教授の確認へつながる。ただし、現時点の実AI記録は会話サービスによる2ターンの比較であり、後日の支援・集計まで同じ実行で確認した記録ではない。完成した一連の実行として見せるには素材取得が必要。

## 01 表紙

**掲載内容**

Architecting an Digital Twin for Scalable, Style-Aligned Instructor Presence

Hikaru Rawin Horinouchi

正式な承認済みタイトルを保持。日付、副題、技術一覧、能力に関する宣伝文は追加しない。長いタイトルを意味のまとまりで改行する。

**読者が分かること：** 何のプロジェクトを誰が発表するのか。

**次との接続：** タイトル中のDigital Twinが、このプロジェクトで何を意味するかを02で説明する。

## 02 教授から求められたもの

**英語タイトル案：** Project requirements

**導入文の意味：** 授業外でも、学生がその授業に即した指導を受け、教授が学生の困難を把握できるようにする。

主ビジュアルは要求の表。原文の長い引用や一般的なAIの説明を置かない。

| 正式概要の柱 | ソフトウェアに求められる具体的な動作 |
| --- | --- |
| 教授の知識を使う | 教授の教材を登録し、授業の根拠を使って学生の質問に答える |
| 教え方を反映する | 説明型・問い返し型などの指導方針を回答へ反映する |
| 学生の利用と教授への還元 | 学生が対話でき、教授が共通する困難を確認できる |

「Digital Twin」はここで「教授の授業知識と指導方針を用いて学習を支援するソフトウェア」という本プロジェクトの意味で説明する。教授本人の完全な再現という意味にしない。

**読者が分かること：** この発表で何の達成を判断すればよいか。

**次との接続：** これらの要求に対して実際に開発したWebアプリを03で見せる。

## 03 開発したアプリケーション

**英語タイトル案：** Course Digital Twin

**掲載する説明の意味：** 教授が教材と指導方針を設定し、学生が授業について対話し、教授が学習上の課題を確認するWebアプリケーション。

主ビジュアルはIT5004の学生画面を大きく一つ。スクリーンショット内の文字をすべて読む必要がないよう、科目名・質問・回答と教材参照の必要部分を切り出す。架空のUIを実画面として作らない。

画面に添える説明は次の3点。

- 教授が用意するもの：教材と指導方針。
- 学生が利用するもの：授業の質問への応答と、条件に応じたチェックイン。
- 教授が確認するもの：記録と学習課題の集計。

画面上に見えていない教授機能は「この画像に表示されている機能」と誤解されない位置に短い本文として置く。実装の存在と、その教育的な効果は分ける。

**必要な注記：** 研究用プロトタイプ。教授本人の指導再現と実学生の学習効果は未実証。実AI候補の画面を採用する場合は、実験構成であることも表示する。

**読者が分かること：** 作ったものの形、利用者、入力と出力。

**素材の状態：** IT5004での会話サービス実行記録はある。対応する実画面は取得が必要。旧科目のスクリーンショットは使用しない。

**次との接続：** 04で発表の道筋を示し、05で利用者の操作を一周する。

## 04 発表の道筋

**英語タイトル案：** Presentation outline

6章を番号付きの簡潔な一覧にする。独立した章扉は追加せず、各ページに現在の章名を同じ位置へ表示する。

1. Project requirements and the application — 何を求められ、何を作ったか
2. Course knowledge — 教材をどのように回答へ使うか
3. Teaching approach — 指導方針をどう反映し、比較したか
4. Continuing student support — 一回の質問の後もどう支援するか
5. Instructor review — 学生の困難をどう教授へ戻すか
6. Current system and further development — 今の選択と次の改善

**読者が分かること：** どの順に要求への回答を聞くか。実装・比較・結果は各機能の章で扱う。

## 05 一連の利用の流れ

**英語タイトル案：** How instructors and students use the system

主ビジュアルはdraw.ioによるUMLアクティビティ図。教授・アプリ・学生の3区画で責任を明示する。目的は全体の利用を理解することであり、API、DB、監査内部の分岐は後続の図で示す。

掲載する主経路：

1. 教授：IT5004教材と指導方針を用意し、公開する。
2. 学生：科目を開き、授業について質問する。
3. アプリ：公開教材と方針を使用して回答を作成し、対話を保存する。
4. アプリ／学生：条件を満たせばチェックインを送り、学生が返信する。質問が最初になくても開始できる別の入口を明示する。
5. アプリ：利用可能な学習課題のシグナルを集計する。
6. 教授：集計・改善案を確認し、必要なら方針や教材を見直す。

制作時は実コード上の順序と権限を照合する。学生の任意の返信を必須にしない。教授のレビューを各回答の事前承認に見せない。チェックインを全員への無条件配信にしない。集計表示には人数などの条件があるため、対話一件から全員向け分析が成立する図にしない。

短い本文で「教授の公開内容を使う対話、条件付きの継続支援、教授による見直しがつながる」と説明する。図は実装の利用フローであり、一つの実証済み長期試験の結果ではない。

**読者が分かること：** 誰が何をし、アプリが間で何を引き受け、結果が誰へ返るか。

**次との接続：** この利用を支える部品を06で示し、まず教材を回答へ使う部分を07以降で追う。

## 全編の接続を改善する編集指定

| ページ | 制作時に解消する読みにくさ |
| --- | --- |
| 06 | C4の各部品が05のどの操作を担うかを添える。知らない箱の一覧にしない |
| 07–08 | 同じIT5004の教材・質問で、入力から応答まで追う。関数名の横に役割を記す |
| 09–10 | 失敗の説明と改善の証拠を対にする。歴史的評価と新しいIT5004例を同一試験に見せない |
| 11–12 | 設定の項目一覧で終わらず、同じ質問に対する実応答のどの部分が変わったかを示す |
| 13–15 | モデル一覧を主題から切り離さない。回答を作る役、検査する役、評価する役を先に定義する |
| 16 | 何が実装できたかと、本人の再現について未立証なことを同じ要求に対して整理する |
| 17–18 | 最初の学生質問なしでも始まる条件付き支援を明示する。送信の契機と判断を結ぶ |
| 19–20 | 保存項目が後日の判断にどう使われるかを示す。ER図を単独のデータ辞書にしない |
| 21 | 長期動作の結果を、継続的な指導の有用性についての限界と接続する |
| 22–23 | 学生の何の記録を集計し、教授が何を変更できるかを一続きにする |
| 24–25 | 教授の変更・障害が05の流れに与える影響を具体的に示す |
| 26–28 | 02と同じ要求に答え、現時点の採用判断、次の変更と確認条件へ進む |

「I could not validate…」は失敗を説明する候補素材として保持する。独立ページを追加する判断は保留し、09または14の結論を支える場合に使う。原因を調べずに教材不足やモデルの誤回答と断定しない。

## 文章設計の読者別レビュー

- 初見のCTO：02の要求、03のプロダクト、05の利用の順で理解できる設計。実画面が旧科目のままでは不整合となるため差し替えが必要。
- Lek教授：本人の概要の3本柱に対応し、継続支援を追加の開発貢献として置く。本人の教材と本人の指導スタイルを混同しない。
- ソフトウェア工学の評価者：利用を先に定義し、後続で設計・比較・失敗・判断を説明する。図の表記だけでなく実装への対応を確認する。
- 専門外の聴衆：冒頭ではモデル名や検索手法を要求せず、人物・教材・質問・結果で説明する。
- 発表者：各ページの役割と次への接続を明記。口頭で画面の意味を補わなくても読めるようにする。

これは文章と構成のレビュー。完成スライドの可読性、文字サイズ、図の密度、発表時間はレンダリングと通し確認後に判断する。
