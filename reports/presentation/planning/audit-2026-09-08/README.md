# アプリ画面の監査：学生の支援受信から返信まで

2026-09-08。ユーザーの指示に従い、開発の優先順位を決めるために実画面を確認した。Product Design auditの手順で、現在の画面を取得し、保存した画像を再確認した。学習効果や全画面の品質の実証ではない。

## 対象と取得条件

- 学生：`http://127.0.0.1:5180/student`、教授：`http://127.0.0.1:5178/professor/setup` と `/professor/delivery`。Codexのin-app browserを使用。
- 既存の録画環境。合成の教授・学生・Systems教材、仮想時刻、既定の決定的な応答生成。実際の外部モデルの品質を今回の画面から判定しない。
- 保存した学生画像は376×863。今回、見た目を整えるためのviewport変更や画面加工は行っていない。
- 授業を開くことで現行アプリが空の合成会話を作成した。返信ボタンは下書きだけを作り、送信は行っていない。設定変更、教材投入、環境の再起動は行っていない。

## 確認した順序

1. 学生の授業画面を開き、現在の目標と未読表示を確認。
2. 通知のベルからTutor check-insを開き、表示順と目標を確認。
3. 下へスクロールし、届いたメッセージと出典表示を確認。
4. Reply in chatを押し、返信入力に移った状態を確認。送信せずに停止。
5. 教授のTwin setupを開き、下書きと五つの準備段階を確認。
6. Course deliveryで公開中の授業と自律支援の状態を確認。
7. Activityで配信・抑止の記録と検査表示を確認。

## 学生の画面：採用した画像と所見

### 1. 授業を開く

![学生の初期画面](/Users/hikaru/Documents/dev/digital-twin/reports/presentation/planning/audit-2026-09-08/01-student-start.jpg)

授業名、現行公開版、教材への範囲、学習目標が表示される点はよい。一方、未読8件の支援はベルの数字で示され、中央は「質問を始める」提案が中心になる。自分から届いた支援を読む動機と次の行動を、主画面から読み取りにくい。

`Demonstrate the approved objective...using the approved course evidence` という長い目標を、続く提案でも繰り返す。学生向けには対象概念と課題を平易に示し、内部的な承認条件は適切な説明箇所へ分ける。**U01/U04**。

### 2. 受信箱を開く

![受信箱より先に並ぶ設定と過去の目標](/Users/hikaru/Documents/dev/digital-twin/reports/presentation/planning/audit-2026-09-08/02-student-checkins.jpg)

受信同意、静かな時間帯、7日間の停止が分かる点は維持したい。ただし、設定の後に目標と学習記録が続き、通知を押したのにメッセージへ到達するまでスクロールが必要になる。

「1/3 active」と表示される一方、先頭3件はexpired / cancelled / expired。コードは全件のactive数を計算し、表示は先頭3件に切っている。この状態では進行中の目標が見つからない。**U01/U02**。

### 3. 届いた支援を読む

![教材全体と記録用の説明まで含む支援メッセージ](/Users/hikaru/Documents/dev/digital-twin/reports/presentation/planning/audit-2026-09-08/03-student-message.jpg)

出典のタイトルと位置が併記され、送信日時を確認できる。個人の受信箱であることも明示されている。

一方、メッセージは二つの概念と録画用素材の許可・合成データの説明まで含む長い本文になっている。「この文から何を説明すればよいのか」が具体的でない。合成教材の構造と生成経路の両方を確認する。**D01/Q03/A05**。

これは録画用の決定的な出力であり、最新の実モデル候補の一般的な品質不良をこの一画面だけから結論しない。教材を読みやすくする場合も、生成済みの失敗を隠すためにメッセージを手書きの成功例へ置き換えない。

### 4. 返信を始める

![返信欄から元の問いが見えない状態](/Users/hikaru/Documents/dev/digital-twin/reports/presentation/planning/audit-2026-09-08/04-student-reply.jpg)

Reply in chatにより会話へ移り、返信IDは内部で保持される。ところが画面上は元の支援が閉じ、入力欄は `My response to this check-in:` のみで、問い・出典・引用の要約を参照できない。学生は何に答えるかを記憶する必要がある。元の支援を返信欄に結び付けて表示する。**U03**。

この一回の操作ではフォーカス情報が通知ボタンに残っていた。キーボードで返信入力へ移れるかは、再現手順を固定して確認する。スクリーンショットからキーボード操作不可能と断定しない。**U07**。

## 教授の画面：当日のUIツリーとコードによる補足

教授画面は当日操作して確認したが、通常取得画像の右端が欠け、full-pageでの再取得にも重複・空白が生じた。そのため下記の教授画像は**レイアウト監査の採用画像にはしない**。元ファイルは取得経緯の記録として保持する。

- `05-professor-setup.jpg`
- `06-professor-delivery.jpg`、`06-professor-delivery-full.png`
- `07-professor-activity.jpg`、`07-professor-activity-full.png`

当日のアクセシビリティツリーと実装で確認できた内容は次の通り。右側の欠落をアプリの横方向overflowの証拠にはしない。

| 手順 | 確認できたこと・強み | 改善候補と限界 |
| --- | --- | --- |
| 5. Twin setup | Sources / Interview / Policy / Preview / Approvalの段階とブロッカーがある | 既存公開授業と新下書きの文脈を、初見の教授が区別できるか確認する。設定の保存失敗を観測したわけではない。P01/P04 |
| 6. Course delivery | SystemsがPublished、2学生、Approved v1、Autonomy Active。公開版と次の下書きを区別している | `R1.2 local release` とA0/A2の説明が固定文字列。実行状態に合う表示へ。取得前の一瞬のOff/0は読み込み途中で、その後正常に表示された。恒常的な状態不一致とは扱わない。F02/U08 |
| 7. Activity | 配信・抑止・出典範囲等の検査結果が記録され、追跡材料がある | 内部reason code、`0/0 deterministic checks passed`、過去のNext checkは教授が意味を解釈しにくい。検査未実行と内容品質の合格を混同させない。U05 |

録画環境は科目あたり2学生である。教授の学習困難集計には少人数を非表示にする条件があり、集計が見えないだけで実装欠如とは判定しない。また、seedされた公開教材とアップロード履歴の件数が違うことを、実取り込みの欠陥と断定しない。

## 直す順序と確認範囲

1. 未読支援の発見、active目標の整合、返信中の文脈を修正する。
2. 実行構成・配信理由・検査未実行の表示を整える。
3. 会話の再開、教授のプレビューとレビュー、教材と出典の一周を確認する。
4. 回答内容と支援判断は、独立した評価基準に基づいて比較する。

画面修正の確認では、未読0/1/複数、active0/1/複数、過去目標混在、長文、返信切替／取消、送信失敗、狭い画面、拡大、キーボードの各状態を対象にする。全利用者での理解度やアクセシビリティ適合は今回未検証。新規onboarding、実メッセージ送信、引用を開く全経路、認証、障害注入も今回の操作範囲外である。
