## 発表で答える問い

**このソフトウェアは何を実現していて、現時点ではどの構成が最も妥当で、継続的な学習支援にするために次に何を改善するべきか。**

対象は、このプロジェクトを初めて見るソフトウェア工学の専門家。スクリプト、レポート、別ページを見なくても、各ページの入力・処理・結果・結論を理解できることを完成条件とする。

プロダクトの説明は、次の一文から始める。

> 教授が授業資料・指導方針・支援の条件を設定し、その範囲で学生への問いかけや質問対応を行う、授業ごとの学習支援アプリ。学生が質問する前にシステムから働きかけることもでき、その後の対話と活動記録を継続して扱う。

「Digital Twin」という名称だけから、教授の判断や指導を忠実に再現できると推測させない。教授の設定がどの動作に反映されるかを具体的に見せ、教授本人への忠実性は未立証と記す。

- 最初に学生の画面を見せ、「届くもの」「学生が次にできること」「教授が制御するもの」を明らかにする。
- 同じ架空の教授・授業・学生を、準備、初回支援、返信、記録、翌日以降まで追う。技術図でもこの利用場面を繰り返し明記する。
- シーケンス図は、[配信保存とジョブ保存の図](../diagrams/implementation/03-delivery-commit-ja.drawio)の粒度を基準にする。担当、実関数、メッセージ、条件分岐、保存、失敗時の結果を残す。
- 図の上には具体的な開始条件、下には学生に見える結果を置く。関数の呼び出し順だけを説明するページにしない。
- 試した設計は、期待した改善、実際の失敗、原因、変更、残る限界まで本編で扱う。
- 現在の開発コード、評価時に固定した構成、比較実験だけの候補を混ぜない。最後に「今のベスト」をこの区別で整理する。
- 章と目次を入れる。章の開始は内容のあるページに章名を付け、区切りだけのページは増やさない。付録は設けない。

## 共通の利用場面と用語

説明用の場面は、既存の合成データに合わせて「Professor A」「Systems」「Student A1」「cache coherence」を使用する。最初は一人を追い、動画で複数教授・複数学生へ広げる。未録画の振る舞いは「コードから構成した説明例」と明記し、実際の観測結果として見せない。

| スライドで使う語 | 同じページで添える意味 |
| --- | --- |
| 公開版 / published release | 学生が利用する、承認された教材と設定の版 |
| 学習目標 / learning goal | この学生に支援する、授業の特定の学習目標 |
| 支援の機会 / opportunity | 対象学生・概念・発生理由・実行可能期間を記録した仕事の候補。配信済みという意味ではない |
| 観測 / observation | 学生の発言や評価結果に結び付く保存済みの記録 |
| イベント / event | 復習時期、誤概念、未完了など、再判断のきっかけ |
| ワーカー / worker | 画面操作とは別に、期限の来た仕事を処理するバックグラウンド処理 |
| no action | 今回は支援を送らず、その理由を記録する結果 |

この表自体を用語集スライドにはしない。各語が必要なページに短い説明を置く。BKT、PFA、評価指標も同じ方法で扱う。UMLなど一般的な表現を解説するだけのページは追加しない。

### 第3章　質問前に始まる支援

#### 10　質問を送っていなくても、条件がそろえば初回の復習候補を作れる — 1:30

- **結論：** 現行の自動監視は、質問本文を必要としないが、会話の枠や同意・公開状態などを必要とする。
- **開始条件：** Student A1は受講登録済み、現行公開版を利用可能、受信同意あり、支援方針と教材が有効。授業を開いて空の会話が作られたが、質問はまだ送っていない。
- **主ビジュアル：** UMLシーケンス図。学生 → UI／`StudentTutoringService` → `SQLiteStudentRepository`、別の起動としてワーカー／`GovernedAutonomyService`。`create_conversation()` → `save_conversation()`と、後の`observe_events()`を混同しない。
- **順序・分岐：** 対象を確認 → 目標がなければ条件付きで作成 → 時間経過 → `_observed_event()` → `create_opportunity()`。初回の対象場面では「目標作成から24時間以降」。優先する別イベントがなく、条件を満たす場合。未到達／不適格なら候補を作らない。
- **出力：** 学生・対象概念・復習という理由・実行可能期間を持つ候補。まだ受信箱には届いていない。会話を作る操作は受信同意ではない。
- **単体確認：** 何が24時間の起点で、質問が不要でも必要な前提は何か。
- **接続・根拠：** 次に、復習以外のイベントと優先順を示す。S2、S3。コードに基づく説明例であり、新規録画済みの結果ではない。

#### 11　「なぜ今」は、保存された出来事と経過時間で判定する — 1:00

- **結論：** すべての学生に一定間隔で同じ処理を走らせるのではなく、対象の記録を優先順に評価する。
- **主ビジュアル：** `_observed_event()`に対応する順序付き決定表。新公開版と旧会話、現行会話の有無、誤概念、繰り返す混乱、未完了、未活動、以前の配信結果、初回復習時期を実装順に示す。
- **具体例：** 空の現行会話と作成後24時間以上の目標では初回復習が候補になる。返信済み・dismissedなどの条件では、その分岐から新しい支援を作らない場合がある。未活動の既定72時間と初回復習の24時間を別の起点で表記する。
- **表示内容：** 該当した最初の分岐で何を返すか、該当しなければイベントなし。判定表は自動観測に範囲を限定し、全システムの全イベント発生源とは呼ばない。
- **単体確認：** この学生を今対象にする理由は何で、どの条件なら候補が出ないか。
- **接続・根拠：** 候補の理由が決まった後、許される支援行動を選ぶ。S3。

#### 12　支援行動は、教授の許可とイベントに合う候補から選ぶ — 1:00

- **結論：** モデルは許可された候補を提案し、条件を満たすときだけ基準の行動を置き換える。
- **開始条件：** Student A1に復習時期の候補がある。対象概念、教材の根拠、教授の許可行動が入力となる。
- **主ビジュアル：** UMLアクティビティ図。イベントと方針の共通部分 → 根拠の確認 → 基準行動と候補の採点 → モデル提案の検査 → 採用／基準行動を保持／no action。

- **単体確認：** メッセージを減らした候補を、そのまま最良としなかった理由は何か。
- **接続・根拠：** 送る時期を改善しても、届く文章や引用の質には別の失敗が残る。E3。

## シーケンス図の共通仕様

今回基準とするのは、単に細かい関数名を増やすことではなく、**ある利用場面の処理を、分岐と保存結果までたどれる詳しさ**である。

| 詳細図 | 起点 | 図の出口 | 本編内で展開する例外・条件 |
| --- | --- | --- | --- |
| 06 公開 | 教授の教材と設定が下書きにある | 学生が使える公開版／公開不可 | 検査不成立、公開時の確認 |
| 10 初回候補 | 質問のない空の会話、独立した受信同意 | 目標と復習候補／候補なし | 会話なし、時間前、優先イベント、前提不成立 |
| 14 配信 | 検証を通った内容 | 受信箱の保存とジョブ結果 | 保存時の失効、既存配信、未到達・見送り・延期 |
| 15 返信 | 受信箱からの返信、または通常の質問 | 会話・応答・引用の保存 | 根拠不足・曖昧性、モードによる経路 |
| 18 継続 | activeの目標と次回処理を作れる結果 | 後日の機会と再判断 | 停止、期限、上限、現在の同意・権限 |

制作時は次を守る。

1. 図の上に「誰の、どの授業で、何が起きたところか」を短く明記する。主要入力は学生、公開版、概念、イベントなど意味が分かる項目で示す。
2. ライフラインは平易な責務名と実クラス名の2段にする。異なるクラスの`process_due()`を同じ名前だけで表示しない。
3. 呼び出しと戻り、条件付き分岐の`alt`、任意実行の`opt`、参照の`ref`、時間経過をUMLの意味に沿って使う。矢印には処理名だけでなく、重要なデータと結果を付ける。
4. データベースの保存箇所には保存対象を明記する。配信では`proactive_messages`、結果では`autonomous_actions`などを実スキーマと照合し、同時に保存されるものと別トランザクションのものを分ける。
5. 一つの図が扱う条件を明示する。通常経路を詳しく描きながら失敗を無条件成功に変えない。詳しい後続図がある場合でも「保存に成功したら受信箱に現れる」など、そのページの結論は残す。
6. 最下部に「学生に見える結果」と「何をもって成功とするか」を置く。技術的な戻り値だけで終わらせない。
7. コードは図の呼び出し順の繰り返しにしない。採用条件、判定式、固定識別子など、設計の理由を確かめられる箇所を選ぶ。実コード／要約した疑似コード／未実装の提案を明記する。

既存の配信図は詳しさの参考素材。**縦に長い確認用画像を、そのまま16:9に縮小して貼ることはしない。** 16:9で配置を作り直す。必要なら14は通常の保存と見送り、19は停止後の復旧に視点を分けるが、どちらにも起点・終点と相互参照を残す。

## 可読性と単体理解の制作基準

- スライドのタイトルは話題名だけでなく、そのページの主張にする。「Architecture」「Evaluation」だけにしない。
- 各ページは「この場面 → 図または実例 → 分かったこと」で完結させる。前のページで一度定義した用語でも、そのページを読むのに必要な意味は近くに短く書く。
- 16:9、白背景、抑えた配色。1ページの主ビジュアルを一つにする。実画面・図・コード・大きな結果表をすべて同じページの主役にしない。
- 本文は原則22–26pt、図の意味を担うラベルは18–20pt以上を制作上の目安にする。長いクラス名は改行しても、意味を担う文章を小さな脚注へ逃がさない。英語化後に実サイズで再確認する。
- 脚注は略語の短い意味、評価の対象、出典とバージョンに使う。失敗・未達・未統合という結論は本文に残す。
- 同じ範囲の旧案・新案では入力、用語、図の方向をそろえる。違う評価データの値を一本の改善曲線に並べない。
- 予測や学習状態のグラフは、分母、単位、良い方向、シミュレーションか実測かをそのページに表示する。評価効用、実行時の効用、学習効果を同じ言葉だけで扱わない。
- 詰まりやすい14・17・23・25・28は、図の読みやすさを優先して装飾・二次指標・重複説明を減らす。主要条件をスクリプトや付録に移して解決しない。収まらなければページ数と時間予算を再見積もりする。

制作後は、各ページを単独表示し、スクリプトもレポートも参照せず次の点を点検する。

| 点検 | 合格の具体的な状態 |
| --- | --- |
| 場面 | 対象の利用者・入力・起動理由をスライド上で指せる |
| 図の意味 | 各担当、主要な矢印、分岐、出力を平易に言い換えられる |
| 結論 | このページで新しく分かることを一文で答えられる |
| 実装との対応 | 本文の動作が実関数・設定・スキーマに対応し、提案は区別されている |
| 誤解の防止 | 配信と学習、候補と実装、動作確認と品質合格を混同しない |
| 次への接続 | 次の問いが、このページで示した結果や残る問題から自然に生まれる |

この構成段階で確認したのは、各ページに上記の材料を割り当てたことまで。完成スライドの視覚監査と、初見の読者が実際に理解できるかの確認は制作後に行う。
