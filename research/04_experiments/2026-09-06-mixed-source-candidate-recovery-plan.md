# Mixed-source candidate recovery development plan

Instrument: `mixed-source-candidate-recovery-development-001`.

Decision: does one current candidate application preserve source permission,
release/course isolation, source-window feedback and reviewed state when mixed
source inputs pass through publication, withdrawal and clean restore? Prediction:
the cross-boundary invariants hold without relying on the original runtime files.
The baseline evidence comprises separate text/candidate, cohort and recovery tests;
this trial connects those boundaries rather than increasing repeated sample counts.
No replacement model or algorithm is selected.

Use only repository-authored PDF lecture text, UTF-8 transcript and anonymized
Markdown forum content. Two synthetic courses deliberately reuse a source name
with different content. Six learners in course A provide the minimum useful
cohort design: five confusion signals and one active learner without a gap.
Check suppression below five and the exact six-person active denominator, not
population prevalence or concept mastery. Course B is an isolation sentinel.

Use the actual staging FastAPI application, credential/session/Origin handling,
queued ingestion worker, current opt-in question-specific/profile composition,
publication preflight and approved profile. A deterministic injected provider
returns inspectable source-bound proposals; record all calls and zero external
requests. This validates integration, not model semantics, external-provider
reliability, browser behavior, deployed TLS or Docker.

Predeclared gates: unreviewed forum rejection; upload provenance and checksums
across all three formats; persisted queued jobs; valid publication and cited
student response for each source family; no cross-course access; real dialogue
signals with privacy suppression and exact active denominator; review audit
reread; withdrawn release blocks new generation; backup checksums; clean restore
with original runtime path moved aside retains sources, jobs, approved profile,
release states, conversations, cohort/review records and authority failures.
Recheck an active course after restore so recovery cannot pass solely on denial.
No direct insertion of signals, citations or review audit events is allowed.

Emit an exclusive manifest with source hashes/revision/dirty state, per-check
outcomes, response/provider ledger, elapsed time, peak RSS, artifact hashes and
failure classification. Capture every failed stage; no favorable-only rerun.
Source changes invalidate the run. A pass keeps integration coverage only;
failures require a recorded correction and new run ID. No release profile changes.

G6 load audit remains separate: prior serial/concurrent ASGI runs observed
provider overlap and request contracts but excluded production authentication,
network sockets, Docker, sustained arrival rates, saturation, RSS measurement,
independent repeats and semantic quality. This credentialed recovery contract
addresses internal auth integration only. It must not be added to G6 latency
samples or presented as a deployed capacity experiment.


Before the final expanded trial, add two cross-boundary negative cases: a
credentialed cross-origin course mutation must fail without creating a course;
a completed course-B ingestion job cannot create a course-A draft even when the
same professor owns both courses. Earlier attempts remain retained, including the
complete initial journey before these additional negative cases. The staged base
uses its existing immutable historical profile/binding for settings validation;
that binding does not qualify the explicitly injected question-specific candidate.
Approved onboarding policy is a disclosed setup fixture; profile approval, source
review, domain-model creation and publication use the actual professor services.
