# Evidence-strength calibration in instructional generation

## Decision and prediction

The completed generation-model stability dispatches do not justify a model
replacement: every alias has a verified critical profile response, including
an unsupported universal detection guarantee. Some final histories also remain
incomplete after provider timeouts and unknown usage; preserve them as failures,
not silently rerun observations. The earlier V10 confirmation additionally
exposed cross-entity attribution. These are meaning errors despite valid schemas
and source IDs. This plan is written before implementing or generating V11.

Test whether a small general source-calibration instruction improves these
behaviours while retaining useful, profile-appropriate tutoring. It must preserve
entity ownership, implication direction, quantifiers and explicit dependencies;
it must not strengthen a procedure into a guarantee. Do not add a topic-specific
answer, blacklist, external semantic judge, second generation pass or larger
output schema. A citation still provides source association, not verified
entailment. Clear supported rules should remain direct, without indiscriminate
hedging or unnecessary refusals.

## Alternatives and implementation boundary

Control: frozen V10, Luna-low planner and generator, 3000 output tokens. Candidate:
V11 with the same typed operation/schema, routing, model, role budgets, evidence
admission, profile authority, source association and policy. Only its explicit
versioned generation instruction changes. Keep V10 selectable and the release
profile unchanged. Use a distinct implementation/prompt ID and explicit
`v11-luna-low` experimental selection throughout API, worker and evaluators.
No repair of local `partial_without_missing_detail` rejections is bundled into
this comparison. Larger-model V10 results remain Refine, not candidate successes.

Before dispatch, independently review the instruction and plumbing, test actual
factory/worker selection, provider serialization, role identity and unchanged
V10 behaviour. Archive exact source/configuration/input hashes and dirty revision.
The same conceptual typed task may retain its transport name because its JSON
schema is unchanged; the trace must identify V11's different prompt.

## Development evaluation

Use exposed development inputs only. Never read the sealed fresh confirmation
or its shared builder at this stage. Run the 28-case entity/implication packet,
two complete 48-context main trials, two complete 24-condition profile trials,
and the unchanged eight-case boundary and mixed-stage sidecars. The main trials
retain separately executed V4 controls and scheduling seeds7901/7902; model
sampling is not seeded. Use V10 Luna-low's completed stability observations as
an explicitly nonconcurrent development reference, retaining its incomplete
second trial. This is not an unbiased randomized head-to-head model comparison.
Do not claim relative improvement from missing V10 outcomes: calculate paired
wins/losses only where both candidate and reference have delivered reviewable
responses, and report missing pairs separately.

Candidate advancement requires all of:

- 28/28 definite useful short diagnostic responses and zero critical errors;
- at least92/96 useful main targets, both trials at least39/48 and13/16 primary,
  and all12 explanatory moves in each trial;
- all12 context-on profile style responses useful, all six matched contrasts
  appropriate, and every actually dispatched profile binding correct;
- boundary and mixed-stage each at least7/8, mixed stage at least3/4 per stage;
- zero verified critical errors in every candidate delivered turn across all
  packets, with prior critical errors invalidating later targets;
- all planned candidate histories complete with known provider usage and no
  runtime/source-identity drift. Local rejections count as unqualified, not
  correct responses; distinguish provider errors from content failures.

These are prospective engineering gates. Two trials reuse48 main contexts and
four source clusters; they are not96 independent students. Review every delivered
turn with the existing meaning-based rubric, retaining uncertainty as unqualified.
Report raw and primary counts, explanatory moves, profile contrasts, boundary
slices, local/provider failures, available-pair comparisons, latency, tokens and
cost. No output-selected retries or favourable early stopping. At most two paid
runs overlap. Existing role-specific conservative limits remain in force:
main800calls/USD128 per run, profile100/USD20; short and sidecar limits must be

Unknown usage must stop further admission; do not remove this safeguard to fill
missing samples. Archive and register partial/failed runs with the same care.

## Advancement and limits

If all gates pass, freeze V11 and run the still-sealed fresh48-context confirmation
once under its unchanged protocol, followed only on acceptance by the permitted
32-case real-course diagnostic and same-configuration operational, authenticated
HTTPS and browser verification. A failed gate means Refine and a documented
failure analysis, not a relaxed threshold or an opened confirmation for diagnosis.
All earlier results remain registered. An accepted experimental profile must link
to the exact evidence/configuration and retain V10/control; it does not establish
real professor fidelity, student learning, institution-wide reliability or the
broader representative400/200/200 completion design. Update the English report
with both the resulting behaviour and those limits.
